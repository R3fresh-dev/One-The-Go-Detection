## Corrections and adversarial disposition

| Finding | Reviewed correction and limit |
|---|---|
| SRV-01: an initializing invocation could enter SQL after an empty drain observation | Admission is closed atomically before stopping sources. Every lease transaction condition-checks the exact open admission owner, generation and source. Previously admitted producers retain leases through SQL disposal. Reopening condition-checks closed ownership and the observed producer epoch, refusing concurrent maintenance. Semantic DynamoDB interleavings test these conditions; they are not live DynamoDB isolation evidence. |
| SRV-02: a generic successful maintenance response could admit the wrong operation | The caller checks the immutable image, function ARN, exact IAM/database role, source/account/profile and effective handler. Both the command and `OTGD_LAMBDA_HANDLER` must select maintenance; entrypoint/working-directory overrides and image-configuration errors refuse. The bounded strict response must match the requested operation, operation-specific status, nonce and closed ownership. |
| SRV-03: a development runtime could accept production configuration | Settings and secret initialization require QA transport mode plus the explicit Ohio `serverless-development` profile. Serverless production refuses. The QA alias does not admit canonical QA acceptance, production promotion or a store release. |
| SRV-04: long streaming/client timers implied a longer first-header budget | The guide identifies CloudFront's sixty-second first-header/idle origin bound separately from Lambda/API streaming and client deadlines. Actual cold/resumed-database HTTPS acceptance remains unexecuted. |
| SRV-05: the independent human operator roles could not load the master secret | Each MFA role receives the exact master-secret read and corresponding Secrets Manager key/context decrypt permission. Runtime principals do not inherit those roles. A separately prepared private operator network path is still required and was not exercised. |
| SRV-06: price parsing and hashing read different file snapshots | Both now use the same bounded, no-follow, stable regular-file bytes. Estimate assumptions include retained privacy cleanup and distinguish average database capacity from the configured maximum. The estimate and alert are not a spending cap. |
| SRV-07: rollout readmission checked only an originally selected run | Before each mutation stage, the caller now checks the actual current default-main ref and newest trusted exact-source run before and after the full thirteen-job proof. A separate newer pending, failed, canceled or successful run cannot be replaced by the original evidence. Main advancement and run changes during proof collection refuse. These are observable rechecks, not an atomic lock on GitHub. |
| SRV-08: missing restore software was described as an unexecuted check | The guide, design and alignment report now explicitly identify the absent Aurora/Lambda restore/reconciliation adapter. This remains an implementation gap for that optional operation; it is not externalized as merely a future test. |
| SRV-09: migration evidence was absent from the recovery journal | Migration writes `migration.json`, matching the existing stage journal's actual path/hash inventory. The workflow preserves bootstrap, migration and admission receipts explicitly. |
| SRV-10: closed deployment ownership could not be resumed after failure | The CLI accepts an explicit private bounded closure receipt, verifies its account/region/source/table and current closed owner/generation before mutations, and drains without replacing ownership. Closure evidence is persisted privately and uploaded explicitly when the runner reaches artifact publication. Missing evidence, incompatible protocols, changed source/ownership or first-establishment failure require reviewed recovery; routine retry cannot reset a retained journal. Hard runner loss is not proof that an artifact was uploaded. |

The ordinary dispatcher uses a maintenance *kind* for its lease but has no closed-admission exception. That exception additionally requires exact deployment ownership and the dedicated administrative runtime role/profile. API, queue and ordinary sweep producers remain denied while closed. Runtime IAM can read and condition-check admission; it cannot open or steal it.

The DynamoDB table contains runtime/admission metadata rather than participant payloads. PostgreSQL remains application authority, and versioned S3/KMS journal continuity remains independently required. `recovery_required=false` does not disable cloud `require_authority`. Cleanup wake calculations retain outbox, lease, artifact, raw-retention, export and recurring deletion deadlines. No genuine study, device, model or clinical authority is seeded by deployment.
