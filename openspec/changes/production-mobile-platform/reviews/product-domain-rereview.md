## Additional targeted contract clarifications

### RER-001 — logout receipt replay after family revocation

- **Severity:** Medium.
- **Status:** Resolved in specification.
- **Source:** shared §2, design §§4–5, AND-AUTH-005 integration.
- **Concrete counterexample:** `POST /v1/auth/logout` revokes the current `origin_jti` family, but its successful response is lost. An identical replay now fails the universal revoked-family middleware before it can return the promised idempotent receipt. Reusing an old persisted intent after fresh login also must not mistake another family's receipt for revocation of the new family.
- **Required correction:** State whether a narrow same-family minimal-receipt replay exception is permitted, or whether the endpoint intentionally returns 401 after revocation and the app represents remote receipt as unconfirmed. In either case, scope logout idempotency to the token family and never exempt ordinary record access from revocation. The issue was sent to the shared-contract owner immediately.
- **Verified correction:** Shared §2 now scopes logout idempotency to `origin_jti` and permits only exact same-family/key/body/generation replay of the accepted minimal receipt after signature/issuer/expiry checks. Changed content conflicts; all other revoked-family requests remain 401. A client that already discarded credentials stays signed out and reports an unconfirmed remote receipt. The reviewer read this amended clause; implementation behavior remains untested.
- **Required implementation evidence:** Lost logout response, exact same-family replay, changed-body/key misuse and later fresh-family login. Confirm that no old family can read data and no receipt from another family is presented as current-family revocation.

### RER-002 — fixed task presentation lacks a concrete style profile

- **Severity:** Medium.
- **Status:** Resolved in specification.
- **Sources:** AND-SET-002/004 integration; AND-TASK-001/008; reaction-task-config-v1.json `presentation`.
- **Concrete counterexample:** Settings requires stimulus colors/luminance/size to be fixed by task configuration independently of theme. The new exact configuration fixes rectangles and labels but supplies no colors, text/stroke sizing, or named digested style profile. Android and iOS can select different visual styles while claiming the same configuration hash.
- **Required correction:** Freeze the developmental software presentation constants, or an exact named style profile with its hash, and distinguish them from unqualified physical luminance. Keep general app theme independent. Update the configuration/fixture identity consistently and retain the declared changed-configuration version rule. The issue was sent to the native and shared-contract owners immediately.
- **Verified correction:** AND-TASK-001 and configuration `presentation.style` now fix requested sRGB colors/opacity, arrow polygon/mirroring, border/corner/fixation sizes, platform font-family policy and 32/20/16-point text, fixed task text scale, layout refusal and theme independence. They prohibit app brightness overrides and explicitly mark physical luminance unmeasured. End task's fixed rectangle provides a 48-point target at the minimum height, with platform minimums and cancellation precedence outside response scoring. The final pre-code configuration digest is `61bd03244a9f82fdc5a1a2b6658483ca201ab5d39a95e64cde0d00f1d5a666c3`; the reviewer checked its identity and all three updated schedule/configuration hashes. Native rendering has not been executed.
- **Required implementation evidence:** Both native views read the fixed configuration; theme changes cannot alter stimulus/targets, and captured metadata identifies the actual presentation profile and any adaptation.

## Independent root/native contract checks

The review additionally traced the new cross-feature contracts through their owning documents:

- The generation barrier in shared §3 matches platform §7's durable database intent plus independent journal acceptance, same-key resumption after a 503, restricted receipt exception, and restore watermark. A completed all-data deletion remains `awaiting_generation_ack` until **Start a new empty workspace**. Normal writes, workers and stale queue payloads cannot adopt a new generation automatically.
- Shared §6 and native device/measurement clauses distinguish an authenticated P-256 binding from analytical qualification and bind the exact normalized values to session/attempt/authorization/configuration/boot/sequence. A signature over payload A cannot qualify altered selected values B. The current repository supplies no approved human configuration.
- Shared §5 and native CHECK/SAL/EYE/HR/ECG preserve a strict v0.1 selected projection plus bounded companion evidence. Finalization binds both hashes; alternative cardiac modalities remain reconstructable while exactly one is selected. Raw images/waveforms cannot be hidden in structured metadata.
- Shared §7 and platform §§4–8 align selected-export bounds, immutable S3 versions, privacy-job vocabulary, current authorization, logical expiry, cleanup and honest partial-failure states. The frontend cannot label a requested cleanup as completed physical deletion.
- Platform §§1–3/9–10 and AND-ENV-003–007 distinguish real LocalStack integration from mocks, environment-specific Cognito and keys, immutable deployment inputs, operational objectives and executed evidence. Source/lockfile/template work does not establish a native binary, hosted service, or physical-device pass.

## Review gate
