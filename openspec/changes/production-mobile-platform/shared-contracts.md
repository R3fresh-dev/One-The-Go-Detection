# Shared application contracts — reviewed implementation baseline

This document is normative for all 20 feature specifications in this change. It resolves cross-feature findings in the independent review reports. Where an earlier HLD/LLD/API description differs, the specific replacement below governs this software change. Scientific gates and approved human-study configurations remain separate and open. This contract does not claim implementation or deployment evidence.

## 1. Release and workspace policy

The historical measurement-only baseline fixes `inference_available=false` and
rejects every legacy `0.1.0` result carrying `research_estimate` as
`UNSUPPORTED_RESEARCH_RESULT`, including live, cached, historical and imported
records. An operator record, remote flag, paired device or preference cannot
enable research behavior in that older binary.

The separately reviewed [authorized model execution change](../authorized-model-execution/proposal.md)
extends this contract for the new service and mobile binary only. Result `1.1.0`
may carry a research estimate after current independent study, consent, model,
artifact, evaluation, acquisition, calibration and recovery authority admission.
The reader verifies the complete new schema and its authority/evidence hashes;
it never promotes a legacy result. Capability becomes available only for the
current authorized account and qualified channel scope. Guest preview and
ordinary measurement/practice behavior remain measurement-only. No real study,
human model or scientific qualification is provisioned by deployment. Software
admission is research-only and never establishes clinical or driving clearance.

Versioned supersession is explicit: the fixed-false and blanket research-result
refusal clauses in this baseline's detailed sections describe the historical
`0.1.0` measurement-only policy. The six matching MODIFIED requirements in the
authorized model execution change govern the new `1.1.0` reader/service behavior.
All unrelated owner, generation, target-time, provenance, explicit-upload,
retention, accessibility and native-calibration constraints continue to apply.
The exception never enables an older binary or admits a legacy-shaped estimate.

| Environment/workspace | Permitted local behavior | Permitted cloud writes |
|---|---|---|
| Guest demo in any build | Fictional chemistry/sensor fixtures; actual native reaction practice with `prototype_sensor` and `uncalibrated` provenance; local export | None. Signing in never migrates guest records. |
| Signed-in local or QA engineering account | Explicitly labeled fictional fixtures in that account's separate namespace | Explicit profile Save and explicit Upload check after current notice acknowledgment; synthetic fixture records remain synthetic. |
| Ordinary signed-in production account | Optional profile, local uncalibrated practice, permitted measurement-only drafts, history/privacy | Explicit owner-scoped profile/data operations; a record's human-study or verified-hardware provenance still requires current independent authorization. No fictional cloud account/study is provisioned. |
| Authorized research account | Only actual approved channel/configuration scope, with current server authorization for qualified capture | Explicit upload and current study, provenance, consent, retention, generation, and device checks. The present release ships no approved real study or active model. |

Every check first uses **Save on this device** to freeze its local record. Account history/result then offers **Upload check** with destination/scope review. This explicit action creates a queue entry. Profile **Save profile** explicitly requests an account write. **Retry queued uploads automatically** defaults off and only retries previously requested profile/check/artifact operations. Reconnection alone does not override it. Privacy/withdrawal operations already explicitly accepted for submission may retry their original request to reconcile an unknown outcome; their UI states this durable intent. No retry expands scope or invents consent.

The all-fictional Python CLI demo retains its strict requirement that every supplied measurement is simulated. The mobile interactive demo uses a distinct domain adapter, permits actual native task evidence labeled `prototype_sensor`, and remains measurement-only and local. It never relabels real taps as simulated to satisfy the CLI validator.

## 2. Identity, account lifecycle, and local access

QA/prod use the configured Cognito issuer, public client, authorization code + PKCE S256, exact callback, and browser authentication. The API requires RS256, configured `iss`, unexpired `exp`, valid `nbf` when present, configured `client_id`, and `token_use=access`. Access-token revocation is enabled for the Cognito client; `origin_jti` identifies the refresh-token family, with `jti` identifying the individual token. Local/test identity deliberately emits this same access-token claim shape, from a separate local issuer and key. ID tokens are never API bearer credentials. Protected API responses identify the verified opaque account reference so the mobile app never assigns an account partition from an unverified email or decoded token alone.

The API additionally checks the current application account state and application token-family revocation on every protected request. Valid signature/expiry alone is insufficient. Account states are `active`, `deleting`, `awaiting_generation_ack`, and `deleted`. A deleted-subject tombstone prevents automatic account recreation by an old unexpired token. A current deletion receipt may be read through its restricted receipt path; ordinary records/writes remain blocked. The API checks data generation and current policy again at worker commit/download authorization.

`POST /v1/auth/logout` revokes the authenticated `origin_jti` family in the application and returns an idempotent receipt; it does not sign out other token families/devices or delete cloud data. Its idempotency scope explicitly includes the token family. After signature/issuer/expiry verification, an exact same-family/key/body/generation replay may return only the already accepted minimal logout receipt despite that family being revoked. This narrow exception exposes no record content and does not permit any other route or a new logout mutation; changed content conflicts and other revoked-family requests remain 401. A lost-response client that already cleared credentials stays signed out and reports remote receipt unconfirmed rather than inventing one. Mobile logout also attempts provider revocation and browser logout when online. Offline logout immediately removes local credentials but explicitly says remote revocation was not confirmed. It does not promise to revoke a token the disconnected server has not learned about. New fresh browser authentication can create a new family for the same nondeleted account.

Sign-out presents **Keep encrypted records and sign out** as the default and **Remove this account's local records and sign out** as the alternative. Removal requires an additional count-specific confirmation for unsynchronized records. Both cancel protected work, invalidate late responses by workspace epoch, remove refresh/access credentials, and lock the outgoing partition. Retained signed-out records cannot be opened offline; the same issuer/subject must authenticate again. Account B never unlocks A's partition. A still-signed-in account may read permitted cached data offline only after device credential/biometric authentication through the OS; cancel/failure leaves it locked. Backgrounding locks account views. Guest demo needs no account unlock.

Each native account/environment partition uses its own random SQLCipher key stored in Keychain/Keystore-backed SecureStore. OS device-authentication gates account opening through expo-local-authentication; no custom PIN is invented. The app tests secure-storage availability and fails closed if an account store cannot be protected. Key loss offers explicit scoped local reset; there is no plaintext fallback. Tokens, raw measurements, credentials, and account identifiers do not enter ordinary preferences/telemetry. The web demonstration has memory-only storage and no persistent-account security claim.

## 3. Data generation and anti-resurrection protocol

`GET /v1/me/capabilities` includes `account_ref`, `data_generation` (positive safe integer), `account_state`, `notice`, and `server_time`. Every protected mutation carries `X-Data-Generation` in addition to the current access token and `Idempotency-Key`; there is no body-controlled owner. The header is transport metadata and is not added to the strict v0.1 scientific snapshot. Queued writes, context/attempt/artifact records, jobs, outbox events, idempotency records, and local namespaces retain the generation that authorized their creation.

Normal mutation authorization locks the account row and requires the supplied generation to equal the current writable generation before applying or replaying a data-bearing result. Acceptance of a deletion request locks the same row, inserts the durable deletion job/journal intent, increments the generation, and sets state `deleting` atomically. No normal write is allowed until deletion is complete. Stale-generation requests return HTTP 410 / `DATA_GENERATION_RETIRED`, without a deleted profile/snapshot in the response. Pending work remains quarantined until local reconciliation applies the declared deletion scope; a new random session UUID does not evade the generation rule.

An identical replay/resumption of the **accepted deletion request or pending journal intent** is the narrow exception: after authenticating the same subject/family or the permitted restricted receipt context, its original key/body/generation resumes the same pending journal intent or returns only the original minimal deletion receipt even though generation has advanced. The API returns 202 only after the database barrier and independent S3 acceptance event are both durable; journal failure returns 503 while preserving the barrier and same-key resumption. Changed content under that key returns 409. Other old idempotency records have sensitive response bodies erased during deletion and cannot return removed data.

For `all_data`, completion leaves identity intact in `awaiting_generation_ack`. The app displays the deletion outcome and asks **Start a new empty workspace**. `POST /v1/me/data-generation/acknowledgments` with the new current generation, explicit confirmation, and its own idempotency key transitions to `active`. It never imports old local content or grants a new study consent. For `account`, completion leaves a deleted-subject tombstone and removes/revokes the provider account as a durable job step. User-visible status cannot falsely claim provider removal if that step fails. A minimal accepted receipt can remain on the requesting device if authentication becomes unusable before completion is confirmed.

Workers use the original job/event generation, acquire the current account state, and check it again before result/export/artifact commit. A deletion worker is authorized only for its named retired generation and job. The separate durable deletion journal and restore watermark are specified in [platform-contract](platform-contract.md); restore must fail closed when the post-backup journal interval cannot be established. Every accepted deletion event, for both all_data and account scopes, includes a keyed subject reference. When a backup predates account creation, restore or subsequent verified sign-in matches that subject reference to the journal account reference and maximum generation; it must not silently provision generation 1. Recovery also installs a durable authentication cutoff and rejects access tokens whose trusted auth_time predates it; refresh alone cannot bypass this cutoff. Recovered study/capture permissions remain suspended until reconciled with independent authoritative records, and absent records leave those permissions unavailable.

## 4. HTTP consistency and notices

| Condition | HTTP / code | Client behavior |
|---|---|---|
| Missing If-Match on a mutable resource | 428 / PRECONDITION_REQUIRED | Retain draft; fetch authoritative revision. |
| Stale If-Match | 412 / REVISION_CONFLICT | Show compare/review; never auto-overwrite or repeatedly retry. |
| Immutable state or changed idempotency content | 409 / STATE_CONFLICT or IDEMPOTENCY_CONFLICT | Preserve intent and present conflict. |
| Retired data generation | 410 / DATA_GENERATION_RETIRED | Quarantine affected queue; reconcile deletion. |
| Missing/invalid access credentials | 401 / AUTH_REQUIRED | At most one coordinated refresh/replay. |
| Current policy/role/consent denies action | 403 / CAPABILITY_DENIED | Explain unavailability; no refresh loop. |
| Invalid field/unknown property/nonfinite input | 422 / VALIDATION_FAILED | Field-addressable errors; no input values echoed into logs. |
| Request or quota bound exceeded | 413 or 429 / LIMIT_EXCEEDED | Explain bound; obey bounded Retry-After where applicable. |
| Temporary dependency unavailable | 503 / SERVICE_UNAVAILABLE | Retain intent; use permitted retry policy. |

Errors use `{code,message,request_id,retryable,field_errors?,current_revision?}`. Unknown errors become an actionable unsupported/error state; they do not become success or a zero measurement. All writes use actor + method + route + generation + idempotency key + canonical request digest. Account-row serialization plus database uniqueness prevents concurrent first-write duplication. Safe replay happens before stale ETag comparison only within the same current writable generation, so a lost successful response is retrievable. Request IDs are server-generated random identifiers. Minimal idempotency key, canonical digest, and operation-reference metadata is retained for the entire writable data generation; it is never pruned in a way that turns a late retry into a new mutation. Sensitive response content is retained or reconstructed only while the underlying authorized record exists, and is erased with that record. A replay referring to an expired export returns that original job and its expired state, never creates another export. Retired-generation metadata follows deletion/journal retention and the narrow minimal-receipt exceptions above; it never restores removed data.

`GET /v1/app-config` returns the current notice version, SHA-256, locale, and same-origin content route. `GET /v1/notices/{version}` returns `{version,locale:'en',content_type:'text/plain',text,sha256,mandatory}`. The UTF-8 text is bounded to 64 KiB, SHA-256 covers those exact text bytes, and only plain text is rendered. The client verifies digest/version against current configuration, caches the content encrypted for accounts, and acknowledges only the actual displayed version. English is the release language; a locale fallback is visibly identified. External HTML/scripts/redirected arbitrary URLs are not rendered. A content/hash mismatch leaves new protected writes paused. Notice updates do not block authorized history, export, deletion, withdrawal, or sign-out; the acknowledgment itself is exempt from the old-notice gate.

## 5. Context, attempts, and immutable evidence

**Start check** is the authoritative local context-freeze event. It allocates the session UUID and sets `created_at=target_at=context_confirmed_at` from that action's UTC timestamp. It freezes the currently confirmed profile/context revision, selected mode, and applicable configuration IDs. The Home/Profile flow lets the user edit context before Start check. The Profile step inside a created check shows its frozen context; an edit requires starting a new check, not rebinding this snapshot. All fields remain optional where specified. Unknown/declined context is not copied blindly from an earlier check.

The v0.1 session remains a selected scientific projection. A **version 1.0.0 companion evidence contract** carries full application context and attempt lineage. Required server operations, all owner/generation scoped:

| Operation | Contract |
|---|---|
| PUT /v1/sessions/{id}/context | Immutable context record, ETag on first creation, idempotent identical retry. |
| PUT /v1/sessions/{id}/attempts/{attempt_id} | Versioned attempt record. Started attempts may settle once under If-Match; terminal evidence is immutable. |
| PUT /v1/sessions/{id}/evidence-manifest | Bounded ordered attempt hashes, context hash, and selected component mapping before session finalization. |
| GET /v1/sessions/{id}/evidence | Context, manifest, attempt summaries/full permitted structured evidence, with explicit omitted raw-artifact reasons. |
| POST /v1/sessions/{id}/attestations | Device-signed capture envelope bound to an attempt and exact normalized fields; never inferred from a source string. |

`CaptureContext` fields: schema_version, session_id, context_confirmed_at, profile_version_id (nullable for a purely local anonymous profile), profile_snapshot_sha256, history_snapshot_sha256, protocol_id, configuration_refs (ID/version/hash/scope), baseline_refs (empty unless separately qualified), and device_associations (device/binding/boot/hardware/firmware/clock-evidence references). Owner and generation are authoritative transport/database fields. The profile/history hashes cover the exact corresponding v0.1 snapshot objects.

`CaptureAttempt` fields: schema_version, session_id, attempt_id, component (`saliva|eyes|cardiac|task|alcohol`), record_id (the selected sample/capture/task identity), supersedes_attempt_id or null, status (`started|valid|invalid|canceled|not_collected`), source, started_at/ended_at or null, configuration_id/hash or null, quality_flags, component metadata, and approved artifact/attestation references. A not-collected entry has null acquisition times and values. Started is never interpreted as successful. Parent restart settles an abandoned started attempt as invalid/interrupted before later work.

A terminal task attempt that declares a nonnull `configuration_hash` SHALL preserve that exact value in its task projection's `config_sha256`. The attempt cannot describe one configured task while exporting another stimulus configuration. A legacy fictional task with no declared attempt configuration remains explicitly unconfigured; this exception grants no native or qualified acquisition authority.

Component metadata is a discriminated, bounded DTO rather than arbitrary JSON: saliva contains collector/lot/adequacy/volume/dilution/collection/analysis lineage and original report fields; eyes contains camera/geometry/illumination/scale/frame-timing/segmentation metadata without image bytes; cardiac contains modality/rate/gain/scaling/contact/filter/dropped-sample/context metadata without an unapproved waveform; task contains the full bounded native result (66 planned trials, at most 1024 inputs, scoring/timing metadata); alcohol contains the separate alcohol measurement reference. Typed schemas reject unknown top-level fields and malformed component values. Raw frames/waveforms belong only in currently authorized artifact storage, never hidden inside metadata.

Each context/terminal attempt has JCS/SHA-256 over its exact validated JSON. `EvidenceManifest` names its schema/session/context hash, at most 128 unique attempt IDs with hashes, and exactly one selected attempt or null for saliva/eyes/cardiac/task/alcohol. A request is at most 1 MiB; each attempt at most 512 KiB. Exceeding a bound invalidates/stops collection or requires an explicitly new check; it never truncates evidence. Selected IDs, record IDs, sources, statuses, times, features, and units must equal the v0.1 projection. All earlier failed/superseded attempts remain in the manifest. An accepted valid task cannot be replaced by another valid task for a preferred score.

Finalization requires the snapshot digest **and** companion manifest digest and transactionally freezes both. The legacy result `input_sha256` continues to mean the v0.1 snapshot JCS hash. The immutable result database metadata additionally binds `evidence_sha256`, returned by session detail and the `X-Evidence-Sha256` result response header. Consumers verify both known hashes; the legacy JSON result is not silently given forbidden extra properties. A future model requiring a different composite input contract needs a versioned change. Local-only records retain the same companion evidence; cloud history explicitly identifies absent/not-uploaded evidence rather than claiming a complete remote record.

Before finalization, retry of an invalid/canceled attempt allocates a new attempt under the same session and links its predecessor. After local **or** remote finalization, the action is **Start replacement check**: new session UUID, new target/creation time, `supersedes_session_id` pointing to the prior check, no carried-forward physical sample/task/optical/cardiac acquisition. The profile can be freshly confirmed. An administrative correction of a report is a separate authorized revision workflow and cannot masquerade as a newly acquired current check.

## 6. Device proof and qualified acquisition

Qualified human capture in this release requires a fresh online server authorization at each start. Cached capability responses are explanatory only and cannot enable offline qualified acquisition. Offline native uncalibrated practice and explicitly synthetic acquisition remain available. This deliberate first-release rule removes any claim of instantaneous remote revocation on a disconnected device and prevents wall-clock rollback/reboot from extending qualified capture. A future offline qualified-grant design requires its own reviewed monotonic/boot-bound signed authorization contract.

`POST /v1/sessions/{id}/capture-authorizations` accepts attempt ID, channel, registered device/binding where applicable, and exact configuration ID/hash. Server verifies current account generation, notice, study membership/consent, real operator qualification evidence, and supported software/configuration; absent evidence returns explicit unavailable reasons. An authorization is a single-use start reference with a 60-second server expiry, not a reusable offline lease. `POST /v1/sessions/{id}/capture-authorizations/{authorization_id}/start` consumes the issued authorization under account/authorization row locks, validates the current generation/policy and 60-second start expiry, and records server_started_at. Its body carries attempt_id and device_boot_id. Identical idempotent replay returns the same minimal start receipt; a different attempt/boot or second consumption returns 409. The app starts only after that matching online receipt, discards a response whose native round-trip elapsed time exceeds five seconds, and never replays it from an offline cache. The 60-second limit is the start window, not the capture duration; the approved channel configuration bounds capture duration. Server rechecks the started authorization and current scope at attestation/upload/finalization. The current repository contains no qualified real configuration; filling an arbitrary available flag cannot create one.

Binding uses an operator-provisioned P-256 public key in DER SubjectPublicKeyInfo, transported as base64 with a key ID/version and active/revoked scope. Participants have no key-provisioning endpoint. `GET /v1/device-bindings` returns only owned bindings and their current public trust metadata; rotation requires a new registry version and binding. Challenges last five minutes and are consumed atomically under a row lock. The signed bytes are UTF-8 `OTGD-BIND-v1\n` followed by JCS of `{schema_version,challenge_id,environment,owner_ref,data_generation,device_id,key_id,nonce,expires_at,hardware_revision,firmware_version}`. Signatures are ECDSA with SHA-256, ASN.1 DER, base64; malformed/nonminimal encodings or values outside the curve order are rejected. The nonce is 32 cryptographically random bytes encoded base64url. The server, not the client, supplies the full transcript.

Capture attestation signed bytes are `OTGD-CAPTURE-v1\n` followed by JCS of `{schema_version,environment,owner_ref,data_generation,session_id,attempt_id,authorization_id,binding_id,device_id,key_id,boot_id,sequence,configuration_hash,payload_sha256}`. The attestation submits that envelope, its signature, and the exact normalized payload. The server checks SHA-256, signature/key status, scope, current authorization, sequence/replay uniqueness, matching immutable attempt, and exact normalized-value mapping. A valid device signature for payload A cannot authorize snapshot B. Source `validated_sensor` additionally requires actual qualification records; signature authenticity is not analytical validation. Heart-rate, saliva, ECG, and alcohol payloads use their named versioned component DTOs; human telemetry fragments may carry the same signed session/boot/sequence evidence, while CRC only detects accidental corruption.

Unprovisioned BLE is explicitly synthetic and never becomes trusted from its name, MAC address, CRC, or proximity. All commands/responses carry session/attempt/run identity and local workspace epoch; canceled/old-boot/old-sequence/other-account events are rejected. The native task's exact developmental timing configuration and deterministic fixtures are defined by the reaction feature and do not imply qualified physical display/touch timing.

## 7. Export, artifact versions, and privacy jobs

Export entry is typed: `{source:'device'|'cloud',selection:{kind:'single'|'selected'|'all',session_ids:UUID[]}}`. `single` requires exactly one ID; `selected` requires 1–500 unique IDs; `all` has no supplied IDs and snapshots the server-selected owned set at acceptance, rejecting more than 500 records rather than truncating. The summary displays count/date range and the selected check when singular. Changing source preserves the selection and reports unavailable selected records; it never widens to all. Widening scope requires a new visible summary/confirmation. Single-check exports include only that check's context/profile version, complete attempt lineage, separate linked alcohol record, and linked results; unrelated current profile versions/checks are excluded.

The cloud `POST /v1/privacy/exports` DTO is `{selection,format:'json_zip',include_raw,raw_scope?}`. The default is `include_raw:false` with no raw scope. The separately reviewed [authorized raw-export amendment](../authorized-raw-export/proposal.md) adds explicit raw selection only under a current independently approved `raw_export` registry version, current retention/consent and exact owned verified artifact versions. Its scope pins authorization ID/version/SHA, export-notice version/SHA, fresh acknowledgement, `confirmed:true` and 1–128 unique artifact UUIDs. Recording or upload permission alone never grants export permission. The scope list is paginated, bounded to four authorities and 512 KiB per response. Total export data is at most 50 MiB uncompressed and the ZIP at most 64 MiB; a grant may lower either bound. Structured selection remains at most 500 checks and each structured record at most 512 KiB. Unsupported or unauthorized raw requests fail explicitly. Archive paths use fixed prefixes and generated IDs only. The manifest retains schema/JCS versions, hashes, source/qualifier/null semantics, selected IDs, omitted categories, and creation/expiry times.

**Cloud downloads use an authenticated API gateway, not a directly reusable S3 presigned GET.** `GET /v1/privacy/jobs/{job_id}/download` requires the current access token and authorizes owner, current generation, account/policy/consent, completed job, expiry, and manifest before opening a stream. Status returns this same-origin download path without bearer secrets, plus a freshness time at most five minutes ahead. Refreshing status can issue a fresh path/metadata only while the export's 24-hour logical lifetime remains. A copied path grants no authority. S3 remains private to the worker/API task roles and reads pin the exact VersionId.

Download first obtains a bounded exact-version archive and verifies its returned VersionId, byte count and SHA. Current owner/generation/account and raw authority are rechecked after the storage read, before first delivery and before each bounded delivery chunk. Revocation/deletion or expiry detected at those checks prevents further delivery. Bytes already delivered cannot be recalled; the UI/export notice states this limit. Exports logically expire within 24 hours, shortened by the raw grant and earliest source-retention deadline; access checks enforce expiry even if asynchronous S3 cleanup has not physically removed the object. Mobile temporary files are private, removed after the share sheet resolves/cancels and on startup cleanup, and never automatically emailed/published.

Artifact buckets have versioning in local, QA, and prod. Upload tickets are PUT-only into quarantine with a five-minute lifetime, immutable declared media/size/hash, signed If-None-Match:*, and bucket-policy enforcement of the conditional header. Required headers include exact Content-Length, Content-Type, base64 x-amz-checksum-sha256, If-None-Match:*, and configured encryption headers. The host is signed and never rewritten. S3 412 causes completion/status reconciliation, never an unrestricted overwrite. Completion first obtains/pins a non-null S3 VersionId, reads **that version** with a strict byte bound, verifies length/hash/media signature, and rechecks ownership/generation/policy under a commit lock. Every later read/export/copy uses the verified VersionId, never bare current key. A successful conditional PUT prevents routine ticket replay from creating additional versions. The current quarantine object is retained until at least ticket expiry plus 60 seconds, so deletion cannot reopen the conditional-write opportunity. The margin is an engineering minimum, not proof that an already-admitted upload finished; durable quarantine references and repeated cleanup cover late arrivals, and known outstanding cleanup is not reported complete. Accepted VersionId remains mandatory defense in depth. Deletion removes all relevant versions/delete markers when admitted writes have settled; a pending upload cleanup step is deferred without consuming a failure attempt, and lifecycle/reconciliation sweeps incomplete/orphan versions. A stale pre-withdrawal PUT may still transfer quarantined bytes until its bearer expiry; it cannot become accepted research evidence and is cleaned under the bounded quarantine policy.

`PrivacyJob` version 1.0.0 has kind `export|deletion`; common states `pending|running|completed|failed`. `expired|revoked` are export-only, `partially_retained` is deletion-only. It includes job_id, scope, data_generation, accepted_at, started_at?, completed_at?, expires_at?, failure_code?, retained_categories[], policy_version, attempt_count, and allowed_actions. Failed partial work remains failed with completed-step metadata; policy-mandated retention alone uses partially_retained. A retained category must identify category/policy/reason/expiry. Unknown states fail as unsupported, never success. Account deletion may leave only the accepted minimal receipt readable on the originating app if provider credentials have been removed; the app explicitly says when completion cannot be confirmed.

## 8. Separate alcohol API

`GET/POST /v1/sessions/{session_id}/alcohol` stores a version 1.0.0 companion record, never a cannabinoid or extra field in the v0.1 snapshot. POST requires owner/generation/idempotency, registered parent session, permitted source, and the alcohol feature DTO. Before finalization, the selected alcohol attempt/hash belongs in the evidence manifest. Once finalized, neither alcohol nor other evidence is appended/mutated; a correction uses a new linked record/session through the defined replacement policy. GET/history/export preserves the originally selected record and mg/L units. A synthetic engineering parent can contain only an explicitly simulated alcohol record; a human value requires the authorized calibrated breath system and attestation. No THC/PPG-derived alcohol or BAC conversion exists.

## 9. Navigation and software verification matrix

Visible routes: Welcome → Demo introduction/Sign in → Data notice → Home. Primary tabs are Home, Check, History, Settings. Home exposes Profile, Device, Start check/Resume draft, and **Alcohol measurement** (including its default unavailable explanation). Settings exposes Profile, Device, Research access, Privacy & data, accessibility/preferences, Service status, About, workspace switch, and Sign out. History detail links results, immutable evidence, replacement check, and typed single-check export. No feature relies solely on a hidden deep link.

Any route/tab/workspace change or overlay that hides an active native stimulus first requests immediate native stop, settles exactly one invalid/interrupted attempt in its original namespace, and only then navigates. **End task** is immediate; a later sheet may confirm discarding the wider draft, but cannot offer to resume the ended scored run. The orchestration layer guards in-app visibility even if a navigator keeps the native view mounted. Late completion events must match namespace epoch/run ID/hash.

The software baseline is Expo 57.0.27 with SDK-compatible React Native 0.86 and React 19.2.3; Node is at least 22.13. Android minSdk is 24 (Android 7), compileSdk/targetSdk are 36, and iOS deployment target is 16.4 with Xcode 26.4 or newer compatible tooling. React Native Web is 0.21.0. Exact patch versions are frozen through Expo install and lockfiles. Source: [official Expo support table](https://docs.expo.dev/versions/latest/). The software acceptance matrix must include Android minimum supported emulator + current target emulator, one physical Android handset, iOS minimum supported simulator + current supported simulator, one physical iPhone, standard/200% text, TalkBack/VoiceOver, portrait phone layout, focus/background/cancel, camera/BLE denial, and offline restart. Tablets use the responsive portrait phone workflow; altered reaction geometry is unqualified. Physical/scientific supported-device approval remains open separately. Any unavailable toolchain/device is recorded as an unexecuted matrix row, not treated as passing.
