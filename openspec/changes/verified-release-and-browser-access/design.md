# Design and implementation boundaries

Existing deploy/qa.py and deploy/prod.py retain their independent signed service/web release, exact-source provenance for every mandatory aggregate/reusable-workflow job, maintenance/journal/migration/activation sequence and actual AWS account checks. The following hardening applies to those existing operations rather than adding a second deployment implementation.

This delta follows cloud-deployment-customer-access. Its MODIFIED operations apply only after that predecessor's cloud-browser-delivery/cloud-release-orchestration base specifications exist. Strict validation can inspect the pending delta now; archival must follow dependency order after required acceptance, preserving existing local draft specifications. No archive or completed-task status is fabricated while gates or merge enforcement remain open.

Authority/evidence readers open regular files without following links or blocking on special files, enforce the configured cap before allocation, and verify the same opened object's stable identity/size/metadata. Private Ed25519 inputs additionally require current-user ownership, no group/other access and a single link. Keys have an 8,192-byte cap; ordinary signed JSON retains its 48,000-byte cap. Web archives retain 256 members, 16 MiB per member and 128 MiB compressed/expanded limits. Archive digest and contents come from the same bounded snapshot. Public HTTPS checks request identity encoding, stream only the expected artifact size plus an overrun sentinel, and reject changed bytes, missing/duplicate/weakened CSP directives or required transport headers.

CloudFront publication and DNS share one actual distribution admission check: Enabled and Deployed, exact regional S3 bucket, exact releases/<releaseId> path, empty legacy OAI, actual S3 SigV4 always-signing OAC, HTTPS viewer policy and the defined single-origin route. Extra origins, origin groups and cache behaviors are rejected because the supplied infrastructure defines none. DNS registration previews these actual inputs. An absent record uses Route 53 CREATE; a concurrent create makes AWS refuse the operation. An exact existing record is an observed no-op. There is no compare-and-swap guarantee against an administrator changing an existing record after observation; no-op receipts do not invent a change ID or propagation completion.

Store operations use a separate nonsecret configuration referring to the real Expo project, admitted cloud release, trusted keys/evidence and platform-specific store record. Plan validates/list stages without network or mutation. Build and submit recheck live trusted source gates, signed backend/QA authority, actual deployed API/issuer/client/callback and official Expo project/build metadata. SDK commands use a pinned CLI and explicit platform/profile/build UUID, never a latest-build selector. Only committed source is staged outside the development checkout. Secrets remain in protected external bindings/files; unrelated deployment credentials and Node preloads are excluded from build children. QA-store and production produce Android AAB or real-device iOS IPA; simulator/APK guest artifacts remain a separate path. Provider remote versions and actual returned metadata are used rather than assuming version one.

Submission is a deliberate upload/processing request. Android uses the configured internal or production track in draft status with review deferred; iOS public release is not automatically scheduled. Build completion, submission acceptance, TestFlight processing, store review and customer availability are distinct states. Receipts identify actual provider IDs and observations; local edited JSON never replaces remote checks or independently signed release authority. Apple/Google records, agreements, enrollment, signing and applicable first-upload/testing/review work are external.

An optional manually dispatched macOS workflow provides browser-operated plan/build/inspection/status and read-only submission reconciliation after default-branch registration and genuine protected environment/account setup. It refuses fresh store uploads: losing an ephemeral runner must not lose the only pending intent and permit a duplicate request. Initial submission uses the helper on persistent protected operator storage. The workflow is separate from all mandatory pull-request jobs in the exact committed workflows and never automatically builds or publishes on merge. A fixed bounded protected input bundle materializes only into new private runner files. Handoffs use separately keyed AES-256-GCM artifacts bound to repository, source, environment and platform, preserving the exact original signed receipt/intent bytes inside ciphertext. This public repository never uploads plaintext receipts, protected inputs, credentials or native store binaries. Actual GitHub environment protection and intended AWS OIDC roles remain external prerequisites.

Codespaces builds dist-preview through the existing explicit guest exporter with no dotenv, fixed unavailable API/issuer and no account client. Post-start serves that export only, checks its guest manifest and refuses to reuse an unrelated HTTP 200 server. Its generated outputs do not replace ordinary dist or start a hosted session by themselves. Appetize receives only verified source-bound guest APK/simulator archives through a real account.

No protocol-supported portable saliva chemistry, calibrated breath instrument or human ECG electrical-state observer is supplied by the current vendor material. Reference-laboratory collection/import and the pinned digital PPG driver are implemented. Creating another empty adapter or converting an unspecified sensor response would not implement those missing instruments.
