In the following matrices, **positive** means executable engineering behavior exists; **partial** means some specified software is absent; **refusal** means a safe unavailable path exists without its qualified positive implementation; **external** means an experiment, hardware decision, assigned approver or actual deployment is needed. ## Specification validation and evidence limits

`tools/verify_openspec.py` checks unique IDs, normative language, at least two scenario structures per requirement, iOS mention and the fixed feature inventory. Its success does not execute the customer scenarios. Strict OpenSpec validation likewise checks document format, not medical safety, source behavior or operational acceptance. The existing machine map intentionally sets automated-scenario counts to null. Keep that distinction after adding operator/raw/deployment/model deltas; the new platform capabilities need their own requirement IDs and traceability rather than being hidden under the original twenty UI features.

The original LLD §10 proposed specialized normalized tables; canonical storage currently uses typed structured records and immutable bodies plus account/check/artifact/job tables. This is an implementation deviation, not automatically a correctness failure. The acceptance obligation is enforced ownership/generation/reference constraints, immutable lineage, bounded queries, unique replay domains, concurrency and reproducibility. New registry and model work must document which constraints are database-enforced versus checked in application transactions.

Every feature change needs source review and appropriate meaningful tests; mandatory merge checks must all pass on its exact final revision with strictly greater than 80% unit coverage and no skipped required checks. ATDD, components, unchanged performance budgets, actual PostgreSQL/S3/SQS dependencies, all container health and LocalStack API journeys remain distinct. YAML and unit mocks do not establish branch protection or deployed AWS behavior. The [earlier canonical review](CANONICAL_ADVERSARIAL_REVIEW.md) is a point-in-time record of fixed CI/security regressions and CAN-01–07; this alignment audit extends its scope, and does not silently close those findings.
